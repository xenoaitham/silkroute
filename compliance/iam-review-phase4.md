**Criterion interpretation (stated verbatim, per task).** Phase-4 acceptance says **"no wildcard IAM"** (MASTER_PROMPT.md:190) with **"SEC-1 reviews every policy — zero wildcards"** (MASTER_PROMPT.md:189). Read literally as "zero `*` characters in any policy," this is unsatisfiable: ARN syntax *requires* `*` in segments whose value is platform-generated (e.g. `acs:vpc:<region>:<account>:vpc/*` for create-time IDs), OSS/log ARN conventions pin account as `*`, and the canonical deny-insecure-transport pattern *requires* `Principal: ["*"]` in a Deny. SEC-1 therefore interprets the criterion as:

> **No wildcard in the `Action` element of any statement (no `"Action": "*"`, no `service:*`, no partial-action wildcard), and every wildcard appearing in a `Resource` or `Principal` must be one of: (a) an ARN segment that is region-less or whose resource ID is generated by the platform at create time, (b) a name prefix scoped inside the `silkroute-`-owned namespace, (c) a region/account placeholder (`*`) where the service ARN convention requires it and effective scope is bounded by the authenticated account, or (d) `Principal: ["*"]` exclusively inside an `Effect = "Deny"` statement with a `acs:SecureTransport = "false"` condition. Any wildcard in an `Action` element is an automatic FAIL; any Resource wildcard that broadens blast radius beyond the silkroute namespace/account/region must be adjudicated row-by-row below and fixed if indefensible.**

Under this interpretation the Action-element rule is **met everywhere**; every Resource/Principal wildcard is adjudicated in §2 and none is a wildcard-action defect — but one *placement* defect (SEC-4-01) and three least-privilege defects (SEC-4-02/03/04) were found.

## 3. Per-policy review

### 3.1 `silkroute-esb-runtime` (infra/security/main.tf:39-97) — MED findings

What the ESB actually does at runtime: produce/consume Kafka via **alikafka SASL PLAIN** (`infra/compute/main.tf:98-105` — SASL credentials, *no RAM actions involved*, so the policy correctly contains **zero** alikafka actions); OSS object read/write on the lake; KMS-protected reads/writes (SSE-KMS buckets); SLS log writes.

- **Kafka:** correctly absent from the policy (SASL, not RAM). ✓
- **SLS:** `log:PutLogs`/`log:PostLogStoreLogs` on project `silkroute-sg` + the two named logstores (82-94). Exactly what log-producing needs; no read/list grants. ✓
- **KMS:** `kms:Decrypt` on the two named SG key ARNs (76-81, `alicloud_kms_key.oss.arn` / `.rds.arn` — exact ARNs, no wildcard). **Gap:** writing SSE-KMS objects (`PutObject` to `bronze/*`) requires `kms:GenerateDataKey` as well; with Decrypt-only, SSE-KMS uploads are expected to fail at cloud runtime. → **SEC-4-03 (MED).** Verify at activation.
- **OSS:** grants `GetBucketInfo/ListObjects/GetBucketVersioning` on the four buckets and `Get/Put/Delete` object access on **all four** buckets including `silver` and `gold` (62-74). This **contradicts the data module's own grant matrix** (`infra/data/main.tf:9-14`: artifacts read-only, bronze read/write, *silver/gold the ESB never touches*, enforced there via bucket policies with no Allow statement). Because same-account OSS access is allow-unioned across RAM identity policy and bucket resource policy, the identity layer alone defeats the bucket-layer intent: the runtime can write silver/gold and delete artifacts. Also `GetBucketVersioning` is a bucket-config read the runtime doesn't need (CI already holds it at security/main.tf:222). → **SEC-4-02 (MED).**
- **Trust (99-114):** `Principal Service = ["sae.aliyuncs.com"]` — a specific service principal, never `*`. ✓ Honest limitation: AliCloud RAM cannot pin a service trust to one SAE application, so any SAE app in the account could assume this role; mitigated by the policy's narrowness. Additional gap: provider 1.285.0 has **no attribute on `alicloud_sae_application` to bind this role to the app** (schema-verified), so the app→role linkage is not expressible in this IaC; activation runbook must wire runtime credentials out-of-band. → folded into **SEC-4-10 (LOW/INFO)**.

### 3.2 `silkroute-ci-deploy` (infra/security/main.tf:155-300)

- **Action lists:** fully explicit across all 11 statements (VPC, security groups, RAM governance, KMS, OSS, RDS, SAE, SLS, CMS, Kafka, ActionTrail). No `*` actions, no `service:*`. ✓
- **Scoping:** region/account-pinned with create-time ID wildcards throughout; RAM ARNs correctly region-`*` (global service); OSS bucket statements name-prefix scoped to `silkroute-sg-*`/`silkroute-cn-*`. Defensible for a deploy role that owns the landing-zone lifecycle. Remarks: `acs:log:*` / `acs:alikafka:*` region segments could be pinned to `${var.region}`; `*instances/*` (287) is an ARN-format hedge; `kms:key/*` spans all same-region keys; CI can author and attach new `silkroute-*` policies (self-escalation path within the namespace). → **SEC-4-06, SEC-4-07 (LOW)**.
- **Trust chain:** role trust pins the **exact user ARN** `acs:ram::${var.account_id}:user/silkroute-ci` (144) — no wildcard principal. ✓ The `silkroute-ci` user itself holds **no access keys in IaC** (128-132: created without keys; comment states keys are rotated out-of-band so no secret reaches state) and no policy attachment exists for it. ✓ no keys / no user permissions in IaC. **But that is also the defect:** a RAM user with zero policies cannot call `sts:AssumeRole` — the role's trust policy alone does not authorize the caller. As written, the documented chain "silkroute-ci → assume silkroute-ci-deploy" is non-functional. → **SEC-4-04 (MED):** add a minimal policy granting only `sts:AssumeRole` on `acs:ram::${var.account_id}:role/silkroute-ci-deploy`, attached to the user.
- `var.account_id` is the placeholder `123456789012345678` (security/variables.tf:10-13, documented "never a wildcard") — correct for validated-plans; must be replaced at activation.

### 3.3 Bucket policies (infra/data/main.tf:114-162; infra/cn-partition/main.tf:142-169)

Per-bucket JSON: an `AllowEsbRuntime` statement (only when grants exist) pinned to `Principal = [var.esb_runtime_role_arn]` (the exact runtime role ARN from `security/outputs.tf:21-24`) — no wildcard principals — plus the unconditional `DenyInsecureTransport` statement (Effect Deny, explicit Get/Put/Delete actions, `Principal ["*"]`, `acs:SecureTransport = ["false"]`).
