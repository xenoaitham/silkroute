# Control matrix — regulatory obligations mapped to the build

Maple Retail Group is a **fictional** Canadian retailer (300 stores + e-commerce) expanding into Singapore and mainland China; this matrix is an artifact of a **self-directed reference implementation**, not a client engagement. Nothing here is legal advice. Honesty frame (ADR-0002, validated-plans mode): **no AliCloud account exists, nothing is deployed to any cloud** — every status below is one of exactly three: **Enforced in build** (real, running, machine-checked in sim/CI, with the artifact and evidence row named), **Designed, schema-validated** (real in Terraform/code design, never applied), or **Verify at activation** (only a live account can prove it). Where the same control spans the split, the status names which part is which.

Method note: the legal citations reuse the project's primary-source-verified citation set (`compliance/citations-verification-phase8.md` — PIPL Arts. 38/39/40, CAC Standard Contract Measures Art. 7, PDPA s. 26 + PDP Regulations 2021 reg. 10(1), PIPEDA Schedule 1 cl. 4.1.3, and the Alibaba Cloud ICP quotes, all with URLs). Two additions were verified for this matrix against the official sources and are cited with their URLs below: PIPEDA Schedule 1 cl. 4.7 (Justice Laws, cross-checked against an independent rendering) and PDPA ss. 13 and 24 (Singapore Statutes Online, read directly; stated here in paraphrase only, deliberately not as verbatim quotes). Quantitative or build claims cite evidence rows (E-0xx in `evidence/EVIDENCE.md`).

## Known gaps (stated, not hidden)

- **Runtime proof is pending an account.** Every "Designed, schema-validated" row above is provable today only as HCL schema and plan output (ADR-0002); no bucket has ever rejected a cross-region read, no CN KMS key has ever encrypted anything. The static CI suite proves the graph and wiring, not runtime behavior.
- **The masking secret is an env sim dummy.** `PII_MASK_SECRET` defaults to `sim-egress-secret` (`apps/esb/README.md` config table, `PiiMaskingPolicy.java:34`); a real secret store (KMS-backed) is an activation-time move. The keyed-HMAC mechanism itself is real and tested (E-009); the key custody is not.
- **Pseudonymization is not anonymization.** The `msk-`+HMAC transform is deterministic and keyed, so the secret-holder can re-identify; it is defense-in-depth behind the primary control (CN order flow never leaves the CN partition), not a residency solution by itself. The code's own doc comment says exactly this.
- **PDPA s. 13–14 consent is recorded as out of build scope** (CM-06) because no customer-facing collection surface exists in this repo; the exclusion is deliberate and explicit rather than a silently missing row.
- **Sensitive-PII categories under PIPL are not claimed.** This matrix deliberately makes no statement about which fields PIPL classifies as sensitive personal information — the verified citation set does not cover it, and inventing the classification would violate the integrity rules.
- **The CN log project lands with CN activation.** Observability (and the audit trail) is SG-only today; CN log isolation is designed (zero cross-region shipping resources exist) but the CN SLS project itself is deferred (`infra/README.md` compliance hooks, SEC-4-09 remark).
